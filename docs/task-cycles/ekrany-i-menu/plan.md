## Choices

| Choice | Way rejected | Cost if wrong |
|---|---|---|
| The addresses are product code: a pure module `screen-address.ts` reads, writes and resolves them, and `PageAddress` of `email-confirmation.ts` gains going to a fragment, replacing it and listening for back and forward through `hashchange` (D-270) | a router library — D-270 refuses it; addresses in the path — the server serves files and would need routes; a new module for the navigation beside `PageAddress` — two abstractions of one address | functions move between modules; no behaviour changes |
| An address that leads to no existing screen has its fragment replaced with the nearest screen's, with no new entry of the history | keeping the crafted fragment — the resolution repeats at each reload; a new entry — back returns to the address that led nowhere | a different back history after a crafted address |
| `app.ts` tells the game view how it was entered: the form or a registration, a reload, an emailed link or „Anuluj”, a rebuild after a conflict; a sign-in that brings back the kept state of D-211 counts as the form; a rebuild after a conflict stays on the address's screen | Siedziba after a conflict — the player loses the place for something another browser did | one branch and its case |
| Leaving Przejście by any change of screen pauses through `setPaused`, a moment of saving (D-207); a logout or an expiry is no change of screen and pauses nothing, D-212 bringing the map run back paused at the next load | pausing at a logout too — a change of the game state the player did not make, saved before the logout | a different saved state at logout; a case and a line |
| `app.ts` holds the one menu bar through `createMenuBar` (the boundary of `createAccountCard`); the page runs the logout and gives the bar its waiting text and sentence; the bar holds its open state and the request of „Wyślij ponownie”; the game view hands the bar its place through an option | the game view holding the bar — the waiting screens show it with no game | moving the boundary between two modules |
| „Konto” is the shared plain button with a new attribute `aria-expanded` in both forms (D-44, D-265); „Siedziba”, „Programy” and „Wróć do przejścia” are links drawn as tabs, with `aria-current="page"` on the place; the menu stands below „Konto” on `panel`; Tab moves through it, with no arrow keys | a new shared control for the items of the bar — a change of D-44 the task does not carry; „Konto” drawn as a tab — `aria-pressed` would claim a selection; arrow keys — D-42 asks for none, and both forms would need them | a look and its lines of CSS and of the styleguide |
| After an uncertain logout its sentence stands in the menu „Konto”, kept open; only the failed save before a logout stands in the line under the bar (question 11, point 3) | that sentence under the bar too — two warnings of one act in two places | moving one sentence |
| The items of the list of programs are links to `#/programy/{n}`, the chosen one with a bar in `selected` at its left and text in `text-strong`; `#/programy` shows the first program of the list | buttons selected in a group — no address, so back and forward would not move between programs; `#/programy` replaced by the first program's address — the menu's item would never be the address the player is at | the look of one element; one resolution |
| The kitchen-sink page builds the menu „Konto”'s part of an unconfirmed address in its own module from the DOM controls and the pure sentences of `email-status.ts`, which keeps them and loses its DOM row | bundling React for the page — D-269 asks for a change of its build step | the sample and the React menu may drift apart; review catches it |
| Przejście is a new DOM module `run-screen.ts` whose update takes the map run and hands its parts a game state holding it, leaving their signatures | changing the signature of every part — work task 6 discards when it rebuilds the screen | task 6 meets the adapter |
| The program panel takes a mode for Programy, and the game view holds one panel for Przejście and one for Programy | one panel moved between screens — its shown program, a view state, would carry from one screen to the other | the memory of a second panel |
| The sentence beside the inactive „Wyślij” stands once in each row whose buttons it explains, under its lines of sending; the sentence of „Kup” stands once under the heading „Umiejętności” | one sentence above the team — farther from the buttons it explains | a line of layout and its case |
| DOM screens are built once and hidden; React screens are created on entering and disposed on leaving | keeping React screens mounted and hidden — their effects and listeners run on a screen nobody sees | one more render at each entry |
| The page's sentence above the first screen leaves at the first change of screen the game view reports | leaving it to the next reload — rejected by question 12 | none beyond row 10 |
| Three new test files on the jsdom harness — the bar, Postać and the list — make six such files, within D-268's ten | putting the new screens' cases into `account-screen.test.mjs` — a file of 4 377 lines grows further | one file of tests more to keep |
| The order of slices: the styleguide's text first, then the shared control, the pure addresses, the three React parts on their own, and only then the page, the screens, Siedziba and Programy, the coding guidelines last, from the code they describe | the coding guidelines first — they would describe code not yet written; Siedziba before the screens by address — the page's tests would be rewritten twice | a slice waits for another |
