## Two questions at start

- Trust boundary: yes — the task adds HTTP routes to `src/server/**`, which the part map names as the trust boundary of `account-server` (requests from HTTP clients, the account database and its sessions), and a command in the container that changes the role of an account. Every code review of the cycle is told so and checks crafted input at the routes: a request with no session, a session of a player, a session of a blocked account, a body with another account's identifier or address, a role read from the session instead of the database.
- Irreversible operation: no — the cycle blocks and unblocks no real account and runs no command on the server. The role command and the schema migration of version 6 are prepared as code and tests; the human runs the command on the server (task *Human actions*) after the deployment. A change of schema version means a return to an older commit ends in a refusal to start until a forward fix (task question 2, cost accepted by the human); every code review checks that the migration is one step at the end, never an edit of a deployed step. A security-sensitive action reserved to a human: running the role command on the server (D-12); the cycle only prepares it, so the request does not open blocked for it, and the task's human action is listed in the request.
