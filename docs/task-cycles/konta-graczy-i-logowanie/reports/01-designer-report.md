## Questions for the orchestrator

1. Mandatory startup configuration versus default-address invariant. Recommended: normal production start requires database path, session-secret file and fixed HTTPS public origin and fails before readiness if any is invalid. The default developer start (non-production, no account configuration) continues serving static files at its established address, with account API returning explicit unavailable JSON and no insecure or fabricated session. Configured local account testing injects temporary real SQLite and random test secrets into the application factory; browser journey uses a local HTTPS reverse proxy and retains Secure. This avoids hidden generated persistent keys, default account storage and a new unsafe cookie mode. Wrong choice cost: changing default startup breaks an existing invariant; ephemeral account defaults make local accounts disappear silently. Accept this bounded developer mode, or prefer always-configured startup with default-address tests providing account configuration (which narrows the literal current invariant)?

2. Missing Mutation testing rule. D-73 adopts the pinned template, whose rule explicitly requires the author to check tests through mental code mutations where no tool is adopted. Current testing.md omits the rule entirely and selects no tool. Recommend restore that rule from D-73 in this task, with no tool adoption and no new exemption; authors name plausible account and view faults and the tests that catch them. No separate simulation audit or mutation package. The skill says tool adoption for computational parts or a departure is a human choice, so this must not pretend to settle future tooling. Wrong choice cost: ignoring the rule violates D-73; installing a tool or declaring permanent non-use invents an unapproved choice. Accept this narrow restoration and leave adoption choice as a separately reported guideline gap?

3. Unmeasured hash cost. Recommend implement an explicit provisional Argon2id profile memoryCost 65536 KiB, timeCost 3, parallelism 1, hashLength 32, max active hash/verify work 2, no waiting queue (capacity refuses immediately), then prepare the human-run target-image measurement and block acceptance until that exact deployed commit passes measured concurrent hash/verify work under the 512 MiB application limit. Local container measurement can reject/tune the candidate but cannot satisfy player-argon2-deployment-check. Wrong choice cost: calling these final before Mikrus measurement fabricates evidence; deferring all code until that measurement makes preparing its executable impossible. Accept a provisional candidate with mandatory remeasurement after any tuning, never a passing deployed invariant before evidence?

4. Character semantics. Recommend count Unicode code points for password 12–128, never UTF-16 code units; preserve password bytes with no trimming/normalization. Email trims Unicode whitespace with ECMAScript trim, lowercases consistently and requires exactly one @ with nonempty sides, no DNS/dot rule. Bound JSON bodies to 16 KiB rather than invent a restrictive email RFC validator. Wrong choice cost: UTF-16 excludes some valid 128-character passwords; grapheme segmentation varies by runtime Unicode version; looser multiple-@ acceptance is hard to use later. Accept these smallest explicit readings?
