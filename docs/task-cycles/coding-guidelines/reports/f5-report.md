## Choices, evidence, alternatives and costs

1. Compare the union of concrete actual name/version pairs across every owned current manifest/lock against the complete base union, rather than diffing lock lines or subtracting package-wide severities. Names derive from lock entry name (aliases) or npm installation path; aliases in dependency specifications must resolve to that same real name and an exact version satisfying their range. Moving an unchanged pair into another owned manifest does not introduce it. New unignored paths are discovered through shared ownership mechanics. The base is an explicit full existing ancestor commit and uses its own historical map in a temporary Git snapshot. This handles base-only paths and ownership changes independently of the current map, at the cost of local Git/temp-file work.

2. Validate both graph inputs before accepting even a no-new-pair result: paired manifests/locks, matching root dependency maps, complete package tables, exact supported versions, direct/transitive/dev/optional/peer references, ancestor resolution and semver ranges. Optional peer references explicitly marked optional may be absent; other missing targets are unsupported/incomplete. Both package-lock.json and npm-shrinkwrap.json are inspected if present. Lock versions 2/3 are supported; v1, missing locks, workspaces/links, non-registry sources, tags/non-semver specifications, malformed identity and unsupported layouts give no verdict. This conservatively stops some valid future npm layouts; extending support requires explicit fixtures, rather than silently omitting them. Non-npm dependencies remain outside the audit's meaning, but an unsupported source in a graph prevents claiming a complete successful npm comparison.

3. If resolved is present it must name the canonical public npm registry. Decode its URL path and require the package name before `/-/` to equal the real lock identity, including scoped names. Without a resolved URL, identity still comes from the lock's name/path and matching dependency specifications. A source saying `other` while the lock would audit `a` is an unavailable result, not a check of `a`. Unsupported/private registry, git, file or arbitrary tarball sources give no named verdict. This is a supported-input boundary, not a changed vulnerability threshold. The weakest-point RED proved that omitting this check produced false success, and its GREEN proves the mismatch is rejected.

4. Run the already-installed root npm 11.13.0 distribution's npm-registry-fetch and semver through a shell-free local Node bridge, with root declaration, every root lock's exact `node_modules/npm` identity/version and installed package version checked. A nested pinned npm cannot mask another root lock version. NODE_* and NPM_CONFIG_* environment overrides are removed; .npmrc is not loaded by this API path. No installer, npx, global npm fallback or check-time download exists. Alternative npm audit CLI adds aggregate/meta-vulnerability processing that is unnecessary for the adopted concrete-pair policy. The chosen mechanics instead issue only Bulk, with public fixed registry, redirects rejected, zero retries and bounded timeout; a failure is unavailable without automatic Quick fallback. Root explicitly accepted this reversible invocation choice. Technical metadata is not characterized as prohibited by D-33.

5. Send only introduced real names and their versions to the current Bulk endpoint. Match every returned concrete advisory's range to every submitted version of that name using npm's own semver and its advisory options `{includePrerelease:true, loose:true}`. Low/moderate/high/critical matches block; info and nonmatching ranges do not. Validate all advisories, including later irrelevant/info entries, before returning any verdict. Unknown severity, malformed range/schema, unexpected name, missing mandatory fields, bool/nonpositive advisory id, malformed JSON, duplicate keys, invalid response shape and network errors are unavailable. Raw response text is parsed strictly so duplicate keys cannot erase an earlier blocking advisory. A compliant Bulk response omits names with no advisories; `{}` is therefore valid, not an incomplete result inferred from missing per-name rows. As with npm itself, the method relies on the database honoring this protocol; it cannot independently detect an advisory the database omits from an otherwise valid answer.

6. The offline path still verifies complete base/current inputs, pinned local npm and valid exact versions/ranges through its semver, but makes no request after proving the difference empty. Fixture tests prove this distinct path without substituting for the actual method. Fixtures use real Git/Node/semver and replace only the external npm-registry-fetch response with an explicit local double; fake installed npm metadata is part of fixture isolation. Live integration with the root-installed npm client remains unchecked until the installation stage.
