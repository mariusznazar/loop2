# Review of the spec `skad-wiem-o-awarii` (reviewer, first review)

Spec: `.runs/task-cycles/skad-wiem-o-awarii/spec.md`. Base `00aa818e59ab484358970f98af1f4ab61e969e4c`, `.the-way` `294af7fde45323ac1851c014a03071a97fc38d96` (both read back with `git rev-parse`).

Verdict in one paragraph: the spec covers all eight items of *To do* and all eight rows of *Settlements to record*, keeps to what the task settled, and its design for the watcher, the dump and the report route is sound against the code I read. Four places would make the build go wrong or make a human check pass without proving what it claims. None needs a redesign; each is a sentence or a filter. They are graded below.

## Findings

### 1. (medium) The line the report route writes at the first refusal has no stated `failure` value, and a wrong guess defeats the watcher's separate counting

Spec B2: "the first refusal of a window writes one failure line of its own (kind `ReasonedFailure`, code `LIMITED`, place the route's, through `writeFailure`)". `writeFailure(failure, place, error, fields)` in `src/server/log-line.ts:47` takes the `failure` word as its first argument and the spec does not give it. Spec C3 counts as "failures" every line beginning with a failure object "other than the browser's", and as "browser failures" only `failure` equal to `browser`.

Why the answer changes the build: if the builder picks any word other than `browser` (the natural pick for a line written by the server, for example the route's own name), then any anonymous client that sends more than 30 well-formed reports in an hour makes the watcher send the "server wrote failure lines" message, and that kind's six-hour throttle (C4) is then spent, so a real server failure in the next six hours is not announced. That is the very risk the task lists ("fałszywe raporty z wielu adresów ... przykryją prawdziwą awarię serwera") and whose safeguard in the technology report is that browser-caused lines are counted separately ("osobne `"failure":"browser"` liczone przez B osobno"). Question for the orchestrator: what is the `failure` word of the LIMITED line? The review's recommendation is `browser`, so the flood is counted under the browser kind and the server kind stays quiet; the spec must say so and the watcher test must hold a flood case.

### 2. (medium) A4's claim that no `account-block` sentence can pass the `^{` filter is false for two of its four sentences

Spec A4: "Every sentence — `Blocked <address>...`, `No account has the address <address>...` — begins with a letter, so it cannot pass the filter". In `src/server/account-block.ts:89-92` the outcomes `already-blocked` and `not-blocked` print `${email} was already blocked; ...` and `${email} was not blocked; ...`, that is, the sentence begins with the address. The address is only checked to hold one `@` with text on both sides (`normalizeEmail`, `src/server/account-policy.ts:60`), so a registered address can begin with `{`, and such a sentence would pass `grep '^{'` into a file that lives about four weeks. The task requires "i tylko one, bez zdań z adresem e-mail", and its own risk is that an address gets into the file.

Why it matters to the build: the command the maker puts in the skill (E1, A4) is the only guard. Fix: filter on the exact start of the two JSON shapes the command writes (`{"event":"account-` and `{"failure":"account-block"`), not on `{`, and drop the claim about letters. The same should be said in the settlement for row 1 so the decision does not repeat the false reason.

### 3. (low to medium) Row 4's invariant is worded without exception, while A1 makes a failed dump non-fatal

*Foundation entries*, row 4 (the task's row 4 too): "a deployment through `loop2-deploy` leaves the replaced containers' log in `/var/log/loop2-app.log`", method test, `Violated: no`. Spec A1 decides that a failed dump (file not writable, disk full, `timeout`) does not stop the deployment and leaves only a `warning:` line. So by the spec's own design the sentence is false in that case, and the only test it can have is the success case. The foundation step will word the invariant from this spec, so the spec has to say how: the invariant should read that a deployment which dumps leaves the log there and one that cannot dump says so in the deploy log (the second half is also what the task's safeguard for "zrzuty przepadną po cichu" asks for), with a test case for each. Otherwise the invariant is either recorded as violated by design or the builder is tempted to make the dump fatal, which the spec rejects with good reason (a full disk would block the deployment that fixes the game).

### 4. (low) The human check of the GitHub e-mail (E3 step 6) can pass for an account other than the one the scheduled run notifies

Spec D lists, correctly, that the failure notice of a scheduled run goes "to the user who last changed the cron line". E3 step 6 has the human start the workflow by hand with the failure input and "see the e-mail arrive". A run started by hand is the dispatcher's own run, so it proves the setting of the account that clicked, which is the account the scheduled notices go to only when it is also the one that last changed the cron line (a squash merge or a commit under another identity breaks that). The step should tell the human to read who that account is (for example the author of the last commit that touched the cron line, `git log -1 -- .github/workflows/check-address.yml`) and to run the trial from that account, or to report the check as unchecked for the scheduled path. Without it the human can report "checked" on the strength of the wrong account, which the task's *Human actions* item does not intend.

3. **Numbers without a source.** 30 reports an hour has a precedent in D-105 (30 account messages an hour in total); the rest (6 hours per kind, 6 a day, 24-hour window, 300 s, 100 MiB, four generations, 6 attempts 20 seconds apart) are the designer's choices, none sourced. I would not demand sources; the spec already puts them under *Left to the maker* with "any change is reported, not made silently". The 6 attempts at 20 seconds cover a longer recreate window than the 5 attempts at 6 seconds of `deploy.yml`'s probe, which fits the task's risk of false alarms during a deployment.
