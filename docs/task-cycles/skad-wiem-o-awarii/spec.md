Base: `00aa818e59ab484358970f98af1f4ab61e969e4c`, `.the-way` pinned at `294af7fde45323ac1851c014a03071a97fc38d96`. Parts touched: deployment, account-server, browser-view, agent-workflow, build-tools (the tests that count and lint the new files).

## Intent

When the game fails on the test server, the owner learns of it from a message and not from a player, and the log of the failure outlives the deployment that replaces the container. Four things carry this: a dump of both services' logs into a host file just before every deployment replaces the containers, a root script on the host that reads container state and fresh failure lines every few minutes and calls `pusher` with fixed text, a scheduled GitHub Actions run that opens the public address, and a small route that lets the player's browser report the kind, code and place of an error nothing handled. The `loop2-deploy` skill tells an agent where the record lies, how long it lives, how to read it, and tells the human what to install and check.

## Goals and non-goals

Goals — the eight items of the task's *To do*, and nothing else:

1. The deploy script appends the whole log of both services to `/var/log/loop2-app.log` just before it recreates them.
2. `compose.yaml` gives both services the `local` log driver with its default rotation.
3. The JSON lines of `account-block`, and only them, reach the same file.
4. The repo holds the logrotate configuration for that file.
5. The repo holds the watcher script and its cron file.
6. The repo holds a scheduled workflow that opens the public address.
7. The browser's last-resort handling sends its line to a new server route; the server writes it as a failure line.
8. The skill says where the record lies, how long it lives, how an agent reads it, how the owner learns of a failure, and what the human installs and checks.

Non-goals (named so the maker does not add them):

- No change to what the game logs or how (D-252, D-253): no new event, no new identifier, no change to the coding guidelines' logging scope.
- No heartbeat for the nightly backup (the task's *Out of scope*, D-233's gap).
- No outside service, account or secret (D-13 stays as it is); no token for `pusher` in the repository.
- The watcher does not watch itself and does not read the dump file; the lines of the last minutes before a deployment that only the dump holds are not reported (see decision C3, the accepted gap).
- No alert on the old game `loop` or on `foundryvtt`.
- No change to `deploy.yml` and no change to how the deployment is triggered.
- No per-address limit on the report route, no `sendBeacon`, no `keepalive` on the report.

The watcher runs only read commands on the two loop2 containers.

## Decisions

The decisions are grouped by unit. Each has the way chosen, the ways rejected and what a wrong choice costs.

### A. The record of the game's log

**A1. The dump step in `deploy/loop2-deploy`.**

- Where: one new function and one new stage, run between the build and the start of the containers (`build_image`, then the dump, then `start_container`), so a deployment that stops before it starts containers (input, lock, resources, fetch, build) dumps nothing, and the containers it dumps are exactly the ones `up --force-recreate` is about to remove. Because it follows the build and precedes `up`, `loop2-deploy-keeps-running` still holds: the dump changes no container.
- What it runs: the Compose command of the script's own style, `logs --no-color --timestamps` on `app` and `cloudflared`, no `--tail`, so the whole log of both services; its standard output is appended to the path in a new constant of the constants block (the dump file, `/var/log/loop2-app.log`); its standard error goes to the deploy log file, as the script treats Docker's own output. Bounded by `timeout` (300 seconds, constant) so a stuck `docker` cannot hold the deployment lock.
- A header line goes to the dump file first, in the same append: a UTC timestamp, `loop2-deploy`, the previous commit and the commit being deployed, so an agent can tell generations apart in the file. The header holds commit names and nothing else.
- The result is one line in the deploy log (which reaches the Actions log, so it holds bytes and states only): on success how many bytes were appended (the file's size before and after, not a copy of the output); on failure a line starting `warning:` that names the file and the exit status. Nothing of the dumped content goes to the console or the deploy log.
- Error handling: a failed dump (file not writable, disk full, `timeout`) does not stop the deployment. The deployment goes on and the warning stands in the deploy log and the Actions log. Rejected: stopping the deployment with a new exit code — a full disk or a broken file would then block the very deployment that fixes the game, the worst moment to refuse; and it would add a stage to the list in `loop2-deploy-keeps-running`. Cost of the chosen way if wrong: a deployment with a failed dump loses that generation's log; the warning line is the only trace, and the skill tells the agent to look for it (risk "zrzuty przepadną po cichu").
- The installed-copy comparison grows by three entries — the watcher script, the watcher's cron file and the logrotate configuration — beside the three it compares now, with the same warning-only behaviour. This is the safeguard for the risk that the watcher on the host is not covered by the comparison; it also means the human reinstalls `loop2-deploy` once, which the task already lists.
- Rejected ways: a dump after `up` (the old container is gone); `docker logs` per container instead of Compose (a second command form to allow, the services' prefix and ordering lost); dumping only the lines of the last N hours (the task says the whole log and the `local` driver already bounds it to about 100 MB per container).

**A2. The log driver in `compose.yaml`.** Both services get the driver `local` with no options, so Docker's own defaults of the driver bound each container's log at about 100 MB. Rejected: `json-file` with `max-size` (a second set of numbers to keep, and the task settles `local`), `journald`/`syslog` (settled out by the task). Cost if wrong: a rollback to a commit without the key recreates the containers on the host's default driver, which does not rotate (named in the skill, E2). A test reads `compose.yaml` and requires the driver `local` on both services and no other `logging` option.

**A3. The logrotate configuration, a repository file `deploy/loop2-app.logrotate` installed by the human as `/etc/logrotate.d/loop2-app`.** One stanza for the dump file: rotate weekly, or sooner when the file passes 100 MiB (logrotate checks the size when it runs, daily at best), keep 4 rotated files, compress all but the newest rotated file (`delaycompress`, so the agent's `tail` and `grep` meet plain text in the newest rotated file), `missingok`, `notifempty`, `copytruncate`, and `su root root`. `copytruncate` is chosen so that rotation never creates the file, whose owner is the deploy account and whose name the repository must not hold (D-13); `su root root` covers a log directory that logrotate would otherwise refuse as writable by a group other than root. The deploy script appends by opening the file anew, so a truncated file keeps being written. The file holds no user name. Cost if wrong: lines written during the copy are lost (accepted: a dump is one append per deployment); `logrotate` not running on the host would leave the file unbounded — the human's check (E3) reads `logrotate -d` and runs one forced rotation. Rejected: `create` with the deploy account named (breaks D-13); no `maxsize` (a crash-looping container dumped by many deployments fills the disk of two other workloads).

**A4. The `account-block` lines.** No code change: the command already writes its JSON event line to standard output and its JSON failure line to standard error, and its sentences with the address elsewhere. The skill gives the human the command that runs `account-block` with both streams merged and appends to the dump file only the lines that begin exactly like the two JSON shapes the command writes — the start of its event line (`{"event":"account-`) and the start of its failure line (`{"failure":"account-block"`) — each with a UTC timestamp and the tag `account-block` in front, in the same shape as the other lines of the file (a timestamp, a source, a bar, the JSON line). The filter is on these exact starts and not on a bare `{`, because two of the command's sentences begin with the address (`<address> was already blocked; ...`, `<address> was not blocked; ...`, `account-block.ts` lines 91-92) and the address is checked only for one `@` with text on both sides, so a registered address can begin with `{`; no JSON line the command writes holds an address, and an address would have to begin with one of the two exact starts to pass, which the exact match leaves to deliberate imitation and not to accident (the residual risk of a human who registers or types such an address is named in the skill). Rejected: the human appending the whole output (the risk the task names: addresses in a file that lives weeks); a wrapper script on the host (a second installed artefact, a second test and a second comparison, not in the task's installation list); writing from inside the container to the process 1 stream (unproved in the unprivileged LXC, silent when it fails, and it changes `account-block`, which D-137 keeps small). Cost if wrong: a forgotten append leaves the event out of the file; the terminal output of the command is unchanged either way.

**A5. Lifetime, stated once.** The record lives in two places: the running container's log (bounded at about 100 MB per container, until the next deployment replaces the container) and the dump file with its rotated generations (about four weeks, shorter if the size cap forces a rotation, longer for nothing). It survives deployments, rollbacks to older commits (if the installed deploy script is the one with the dump) and a host restart. It holds `accountId` values and the lines of the game for those weeks; the skill and the decision say that as the retention of that data (D-252 scope). Cost if wrong: an agent expecting older history finds none; the skill says four weeks.

### B. The browser's report

**B1. The route `POST /api/browser-failure`.**

- Behind the same gate as the other account routes: it is added to the set of paths the `router.all` gate covers, so the 503 without accounts and the 403 without proxy metadata apply to it, and any other method falls through to the JSON 404. It takes `mutationGuards` with the 16 KiB body limit of the small routes (D-104 says "at most 16 KiB for every other route"; the line it writes is bounded by the field patterns, not by the body limit, so no limit of its own is added).
- No session is required: a failure can strike on the login card before any sign-in. The route reads, but does not require, the session the other routes read: when the stored session names an account, that `accountId` goes on the line; the request's body never names an account. A request with a forged, absent or expired cookie is accepted with no `accountId`. The route issues and renews nothing of its own.
- Body: exactly the three fields `kind`, `code` and `place`, each a string, no other field (the existing exact-fields helper). `kind` and `code` are one word of letters, digits and underscore, starting with a letter, at most 64 characters — the pattern the browser's own `errorWords` already guarantees, so every line the browser writes passes; the word `none` is one of them. `place` is such words joined by `.`, `/` and `-` (for example the two places that exist today), starting with a letter, at most 96 characters. A body of another shape — a missing, extra or non-string field, an empty or oversized value, a space, `@`, a quote, a brace, a line break, a non-ASCII character — gets the existing `invalid-request` refusal (400) and writes nothing.
- Answers: 204 with no body for an accepted report; 429 with the existing `too-many-attempts` code when the limit of B2 is reached; the existing refusals of the guards and the gate otherwise.
- Rejected: a route that needs a session (reports from the login card and from a signed-out page would vanish); taking `accountId` from the body (anyone could name any account in a log that lives weeks); `GET` with query fields (outside D-104 and `account-client-requests`); `sendBeacon` (bypasses the account client and the JSON/Origin discipline, and counts against the page's 64 KiB `keepalive` quota — a report could make the save at „Wyloguj” fail). Cost if wrong: a pattern stricter than the browser's words drops a real report silently — the test feeds the pattern the real words of `errorWords` and the two real places.

**B2. The limit.** One count for the whole server: at most 30 accepted reports per rolling 60 minutes, in memory, reset by a restart, held where the other limits are held so a test can build it with a small limit and a clock. Over it, the route answers 429 and writes nothing; the first refusal of a window writes one failure line of its own (through `writeFailure` with the `failure` word `browser`, kind `ReasonedFailure`, code `LIMITED` and the route's place, so it begins `{"failure":"browser"` like every line this route causes), so an agent and the watcher see that reports were dropped without a line per dropped request; the watcher counts it with the browser failures (C3), so a flood moves the browser kind and never the server kind. The count is taken after the body passes its pattern, so refused bodies use none of it. Rejected: a limit per client address (one more table to bound, and an attacker with a handful of addresses defeats it anyway; the global cap bounds the file and the watcher whoever sends); no limit (the file and the watcher's budget belong to anyone with a browser). Cost if wrong: one address can use the hour's budget and silence real browser reports for the rest of it; the line of the first refusal shows it happened.

**B3. The line written.** A new writer in `log-line.ts` next to `writeFailure`: one JSON object with `failure` set to `browser`, then `kind`, `code`, `place` as sent, then the `accountId` when the session gave one. It reads no error and quotes nothing but the three accepted words. The `place` here is the browser's place; the discriminator is `failure: browser`, which is also what the watcher counts separately. No new event, no new identifier.

**B4. The browser side.**

- `last-resort.ts` gets one optional callback, called with the kind, code and place of a line at the moment — and only at the moment — it writes that line to the console, inside the "not written before" guard, so the report goes out once per distinct line per page load and a fault that repeats every tick sends one report. The handling of the window events and `report()` for the React card go through the same guard. The module still does no network work of its own.
- The account client gets one method that posts the three words to the new path as an ordinary JSON request through the same exchange function — default time limit, `credentials: same-origin`, `redirect: error`, **no `keepalive`** — and returns the usual result type; a failed send is a result, never a throw. `app.ts` passes the callback that calls it and ignores the result; the call is also guarded so that an exception in a test double cannot become an error in the last-resort handler. A report that fails is not reported again.
- The console line and the sentence on the screen (D-253, D-323) are unchanged. D-253's text is not changed by this task; the report is a consequence of D-347's change (see the Foundation entries).
- Rejected: reporting at every `onUncaught` (breaks "the same line once"); a second handler in `app.ts` (two places that decide what is a new line). Cost if wrong: a repeating error with changing words sends one report per distinct line; the global cap of B2 holds.

### C. The watcher

**C1. Files and identity.** `deploy/loop2-watch` (Bash, constants block between the two markers in the style of the other two scripts, tests replace only that block), `deploy/loop2-watch.cron` (`MAILTO=""`, every 5 minutes, as root, the installed name without a dot, per `cron-d-file-rules`). Installed by the human as `/usr/local/bin/loop2-watch` (root, 0755) and `/etc/cron.d/loop2-watch` (root, 0644). Its own log `/var/log/loop2-watch.log`, its state under `/var/lib/loop2-watch/`, its own lock `/run/loop2-watch.lock`. The script takes no argument and reads no environment variable that changes a constant.

**C2. What it reads and how it stays out of the deployment.**

- Reads only: `docker inspect --type container` of `loop2` and `loop2-cloudflared` with one fixed format that yields, per container, its full id, status, health status and start time; `docker logs` of `loop2` for a time window, both streams, counting lines. Nothing else of Docker; the test lists every Docker command the script contains and fails for any other form (the safeguard "test niezmiennika nie obejmuje strażnika" is closed by this test and by the comparison in A1).
- Every Docker call and the `pusher` call run under `timeout` with a kill delay.
- The deploy lock `/run/loop2-deploy.lock` is only looked at, never taken for writing and never created: the script opens it for reading with a plain redirection (which creates nothing; a missing file means no deployment), asks for a shared non-blocking lock and lets it go at once; it does not call `flock` on the path, which would create the file as root and could lock the deploy account out. If the lock is held — a deployment or the nightly backup is running — the run writes one line to its log and ends without touching its state. The lock is looked at again after the reads; if it is held then, the readings are dropped and state is not advanced. A run that drops a window leaves the window open, so the next run reads the longer span.
- Overlap of its own runs: an exclusive non-blocking lock on its own lock file; a second run ends at once.
- Rejected ways of seeing a deployment: reading `docker events` (a 256-event buffer that fills with health checks, a long-running reader that can hang and, as the root's, hold the lock — the technology report's risks 1-3); reading the deploy log (a growing file parsed for a state it does not state). Chosen: compare states, which cannot lose a restart to a buffer and cannot raise an alarm for a deployment's `die` events.

**C3. The five kinds, the window and the state.**

| Kind | Condition |
|---|---|
| down | a container is missing, not running or restarting, or `docker` cannot be read |
| unhealthy | a container's health is `unhealthy` |
| restarted | a container has the same id as in the state and a different start time |
| failures | the log of `loop2` holds, in the window, lines beginning with a failure object whose `failure` word is not `browser` |
| browser failures | the same, lines whose `failure` word is `browser` — the accepted reports of B3 and the `LIMITED` line of B2, so a flood of reports spends the browser kind's six hours and leaves the server kind free |

- A container whose id differs from the state's was replaced (by a deployment or a human's `up`); it is recorded silently and raises no `restarted`.
- The window is from the end of the last completed run to the start of this run, given to `docker logs` as whole seconds; the end is taken at the start of the run so lines written during the reading fall in the next window; a window is never longer than 24 hours. An empty or unreadable state means "from now": it is written, nothing is reported (the lost state file cannot cause a flood).
- Counting is by a fixed anchored prefix of the line (`{"failure":"` and the browser variant); the content of a line is never copied anywhere. Only the existence of a count above zero matters; the count itself goes to the watcher's log.
- The state file holds: the end of the last window; per container the id and start time; per kind the time of the last message; the times of the messages of the last 24 hours. It is plain `key value` data read by a strict pattern per line (digits, hexadecimal, a fixed time shape); a line that fails its pattern means the whole state is treated as missing. It is never sourced, evaluated or put into a command. The script makes its directory (0700) if it is missing.
- The accepted gap, from the task's *Risks taken*: failure lines written between the last run and a deployment that removes the container are only in the dump and are not reported. The skill tells the agent to read the dump after a deployment that follows a report. Not taken: reading the dump from the watcher (it needs the Compose line format with its service tag, a bounded tail, a time filter and a rule against counting a line twice when an `up` fails after the dump; for the few minutes of a window it is the more expensive choice, and it can be added later without touching the rest).

**C4. Throttle.** Per kind at most one message per 6 hours; across all kinds at most 6 messages per rolling 24 hours; the lines held back are only counted in the watcher's log. When several kinds are due in one run they go in the order of the table above until the 24-hour budget ends. A message the `pusher` call reports as failed still counts as sent (its exit status tells little; retrying would be a flood). Rejected: a message per occurrence (the unknown `pusher` limits and the backup's notice, D-233); an interval per kind that re-arms when the condition clears (a flapping container would send every flap). Cost if wrong: a second, different outage of the same kind within six hours is not announced by this channel; the scheduled check (D) still sees an unreachable game.

**C5. The message.** One call of `pusher` per message, as the backup does: a fixed subject per kind and one fixed sentence of text per kind, held in the constants block, in Polish like the backup's; the subjects differ from the backup's and from each other. Text says only which kind of trouble was found (the game is down, a service is unhealthy, the game restarted, the server wrote failure lines, browsers reported failures) and where to look (the `loop2-deploy` skill). It holds no number, no commit name, no `accountId`, no container output and no word read from a log or from Docker; the standard input of `pusher` is that sentence and nothing else. The wording is the maker's, within these limits.

**C6. Its own log.** One line per run that skipped, found something, sent or held a message or ended abnormally — no line for a quiet healthy run, so the file grows only with events. A line holds a UTC time, the run's outcome, counts and kind names; no `accountId`, no Docker or log content. An abnormal end (a non-zero exit, a signal) leaves a line, like the backup's exit handler; the watcher never calls `pusher` about its own failure (a failing watcher would flood). A quiet run still rewrites the state, so the age of the state file shows the watcher is alive; the skill lets the agent read that age.

**C7. Installation facts.** The script stands in the list of scripts shellcheck reads, and its cron file `deploy/loop2-watch.cron` in `NOT_ROUTES` of the route test (they start no image), in the installed-copy comparison of the deploy script, and has a test with stand-in tools on the pattern of `backup_script_support.py` (stand-in `docker`, `pusher`, `flock`, `date` and the others, so a call shows in the record). The `pusher`, cron and Docker behaviour are not proved by it.

### D. The scheduled check of the public address

A new file `.github/workflows/check-address.yml`:

- Triggers: `schedule` every 5 minutes on minutes that are not 0 (GitHub delays runs at the top of the hour; for example 3, 8, 13 ...), and `workflow_dispatch` with one boolean input that forces a failure, so the human can make the one trial failure the task asks for. No `push`, no `pull_request`.
- `permissions: {}`, no checkout, no secret, no SSH, no `github.*` expression inside a `run` script (the boolean input reaches the script through `env`, as `DEPLOY_SHA` does in `deploy.yml`).
- A concurrency group of its own (not `deploy-loop2`), cancelling an older run of the same check; a job timeout of 5 minutes.
- One job, one step: `curl` the public address from the repository's address (the same host as `deploy.yml`'s declared address, checked equal by a test) and succeed only on HTTP 200; up to 6 attempts, 20 seconds apart, each bounded by 15 seconds — enough to ride out the recreate window of a deployment and a blip — then `::error::` and a non-zero exit. The forced-failure input makes the step fail at once.
- Alone it can fail in four ways the human must know: both the server and GitHub down (silence); GitHub disabling the schedule after 60 days with no repository activity; notifications set off or sent to another account (GitHub sends the failure notice of a scheduled run to the user who last changed the cron line); and two messages on a real outage (one from the watcher, one from GitHub). All four go in the skill.
- Test: a new `tests/deploy/` test on the pattern of `test_deploy_workflow.py` — triggers exactly `schedule` and `workflow_dispatch`, `permissions: {}`, no `actions/checkout`, no secret, no `ssh`, the only host is the declared public address, its concurrency group differs from `deploy-loop2`, the step exits non-zero on a non-200.
- The route test (`test_no_other_deployment_route`) gets the workflow, `deploy/loop2-watch`, `deploy/loop2-watch.cron` and `deploy/loop2-app.logrotate` in `NOT_ROUTES` (it counts all four): none of them starts an image, and for the workflow a test shows it deploys nothing. Rejected: weakening the test to skip workflows other than `deploy.yml` (the tripwire exists to catch exactly an unread route); putting the check as a job in `deploy.yml` (a second trigger in a file whose test pins `push` to `main` only).

### E. The skill and the human's part

**E1. `SKILL.md` (both copies).** Additions, all inside the existing four files:

- The resource table gets the dump file and the logrotate file, and the watcher's script, schedule, log, state directory.
- *Allowed* reads gain, through `mikrus`: a bounded `tail` or a `grep` with a fixed string and a limit on matches of `/var/log/loop2-app.log` and its newest rotated file, `zgrep` of the older compressed ones, a bounded `tail` of `/var/log/loop2-watch.log`, the age of the watcher's state file (`stat` of its modification time, never its content), the owner, group and mode of the dump file, `docker inspect --type container --format` of the log driver of `loop2` (expects `local`), and `cmp` of the three new installed files with their sources. Locally, `gh run list` and `gh workflow view` for the check workflow. Still not allowed: any write to those files, reading the state file's content, `docker logs` of a replaced container, running the watcher.
