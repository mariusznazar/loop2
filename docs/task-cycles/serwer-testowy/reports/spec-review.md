# Spec review — serwer-testowy

**Status: Issues Found.** The design covers the task's principal delivery path and respects the human-only change boundary, but the issues below would lead to an incomplete foundation pass or an unreliable deployment and rollback plan. This is an independent review of the specification, not approval of the eventual deployment.

## Blocking findings

1. **The six accepted settlements have no explicit recording map.** The specification says they “bind” the design, then calls for “assigned foundation entries” without identifying where each of the five decisions and the one environment fact will be recorded (`spec.md:9`, `spec.md:42`). The frozen task explicitly calls all six *Settlements to record* (`task-frozen.md:98-109`). The approved project plan also assigns two deployment decisions and three deployment-related invariants to this task (`plan_mvp_loop2.md`, Projected entries, task 2). A plan based on the present wording could implement the route while omitting the read-only agent boundary, access-setting placement, Docker choice, or Cloudflare fact from the foundation. Before planning, list each settlement, its destination foundation entry, and whether it extends a projected entry or needs its own entry; also name the existing serving-process decision/invariant update and the entries intentionally deferred to the account task. Do not silently treat the five decisions as one generic deployment entry.

2. **A commit SHA tag is not an immutable rollback target.** The specification retains successful releases as SHA-tagged images (`spec.md:15`, `spec.md:23`, `spec.md:34`, `spec.md:38`). Rebuilding the same commit after a rollback, retry, or base-image update can retarget the local tag while the history still names it. The retained “successful image” might therefore no longer be the image previously verified. Docker image tags are references that can be changed; [Docker's tag documentation](https://docs.docker.com/reference/cli/docker/image/tag/) describes assigning a tag to an image, and [Docker's immutable-tag documentation](https://docs.docker.com/docker-hub/repos/manage/hub-images/immutable-tags/) explicitly distinguishes mutable tags. Specify an immutable image ID or a unique release tag in the success record, plus behavior when an already built SHA is requested. Test repeated deployment, rollback, and rebuild of the same SHA against the retained history.

3. **Rollback may restore obsolete infrastructure configuration while Cloudflare stays unchanged.** The proposed host port may change after observation (`spec.md:24`), but rollback switches the old release's Compose configuration and explicitly leaves Cloudflare alone (`spec.md:38`). If an older Compose file publishes a different port, a healthy old container could still be unreachable at the public route. The same uncertainty applies to repeated `rollback N`: the specification does not say whether a rollback adds a new successful release or how the next N is counted. Separate the stable host routing and Compose project identity from versioned application releases, or define a compatibility check that refuses an incompatible rollback without disturbing service. Define history ordering after rollback and test port/configuration changes as well as successive rollbacks. [Docker Compose documents that `up` recreates a service when its configuration or image changes](https://docs.docker.com/reference/cli/docker/compose/up/).

4. **The fixed installed scripts need a version-change protocol.** The source of the trigger and deploy scripts is versioned in the repository, but the running copies are installed by a human outside the checkout (`spec.md:26`, `spec.md:44`). A push changing those scripts still invokes the older installed copies; the specification does not say how a script-changing commit reaches the host without violating the human-only server boundary. Specify whether such commits pause automatic deployment pending a human install, how compatible versions are checked, and how the human can recover if the install fails. Include this distinction in the deployment skill. This preserves the valuable fixed-command boundary while making the promised push-to-deployment behavior honest.

5. **The isolation requirement needs a build-stage resource gate.** The existing game must keep working (`task-frozen.md:20-27`), and the task context records a shared host with limited memory and disk (`task-frozen.md:47-50`). The proposed memory limit applies only to the new running container; the host performs `npm ci`, TypeScript compilation and image build before replacement (`spec.md:23-24`, `spec.md:34`). “Building also consumes host memory and must be observed separately” does not define what makes a deployment safe to start or when it aborts. Require a measured preflight and failure rule for host memory and disk, plus an old-game check during or immediately after a build/failure. This is a capacity and acceptance issue, not a request to invent a fixed threshold before observing the host.

## Checks with no blocking concern

- Scope follows the frozen task and the approved plan's later assignments: no accounts, sessions, mail or backup are invented here. The project's older “resolved in server task” labels conflict with the approved plan change log; the specification identifies and resolves that conflict (`spec.md:46-48`; `plan_mvp_loop2.md`, Change log).
- The agent/human boundary is stated consistently: agent read-only via the named MCP, human changes to host and external settings, with a blocked draft until the five human action groups complete (`spec.md:9`, `spec.md:44`; `task-frozen.md:66-72`, settlement 3). The spec correctly avoids claiming that public IPv6 reachability or live deployment is already proven.
- The selected Cloudflare mechanisms match current official documentation: [Origin Rules](https://developers.cloudflare.com/rules/origin-rules/) support destination-port override on Free; [encryption modes](https://developers.cloudflare.com/ssl/origin-configuration/ssl-modes/) place hostname-specific mode in a Configuration Rule; [Flexible](https://developers.cloudflare.com/ssl/origin-configuration/ssl-modes/flexible/) uses HTTP to origin. These documents do not establish reachability of this particular host, so the human verification gate remains necessary.
- The local code and existing invariants support the proposed Node 24, Express 5, type-check and loopback-default design (`src/server/main.ts`, `src/server/app.ts`, `package.json`, `tests/invariants/test_account_server_typecheck.py`). The spec correctly notes that the type-check invariant must be extended when deployment files appear. The verification list is a suitable start once the rollback and isolation cases above are added.

## Verdict

**Revise the specification before implementation planning.** Findings 1–5 change the release model or required proof; they are not wording preferences. The recommended staged-image approach remains viable if those gaps are closed. No server, Cloudflare, GitHub setting, foundation entry, or application code was changed in this review.
