## Approaches and choices

1. **Chosen: split the proposed layout rule.** One entry states that the browser and server use a single shared npm package and lockfile, with no separate application package for either side; one covers distinct TS configurations/output directories. This takes one additional entry and check, but independent breaks identify which D-06 promise failed. Retain the original proposed `application-build-layout` identifier for the compiler-layout half; name the package half `application-package-layout`. The already-written `application-build-output` remains separate.
2. Keep the combined `application-build-layout` sentence. Fewer entries, but a failing test conflates package structure with compiler directories and one deliberate break may only prove half the sentence.
3. Fold both clauses into `application-build-output`. Fewest entries, but that existing sentence and test concern compilation behavior, not the common package. Expanding it would obscure what failed and change an existing binding sentence.

The source proposal offered a split as a question; the task carried the panel's recommendation. The orchestrator provisionally accepted option 1. The source sentences for public files and occupied address are preserved; their `Derives from: none` is important because D-05 says one process serves files but does not specify the static directory or occupied-port behavior. Public/occupied entries are recovered from existing behavior and therefore need recovered rows; the D-06-derived entries do not.

The pinned decision template makes the merged log append-only, including field-only corrections. The foundation implementation therefore appended three `unchanged sentences` versions in commit `d5feaf9`, leaving /1 intact. D-04/2 explains that its narrower violation example distinguishes the game's own code from external libraries and rejects keeping the overbroad example. D-05/2 explains that *Origin* links the partial decision to its full approved source and rejects leaving that link absent. D-06/2 explains that *Verification* must name the package and compiler-layout checks alongside compilation and rejects leaving verification limited to compilation. Their binding sentences and fingerprints stay unchanged; `Mariusz, merge of <request link>` is the pending approval form. This choice follows ruling C9/C10 in the cycle record and avoids a historical edit that the format guard would reject.

For `npm ci`, the pinned invariant template permits a *Method* consisting of one command, one assessment file path, or `TODO`, and only five named fields. A new prerequisite field or a shell chain would break that form. The chosen interpretation is a short preamble immediately under the file title, before the invariant entries, and unchanged single-command *Method* values. The existing test helper already fails with `run npm ci first` when `node_modules` is missing. The orchestrator provisionally accepted the preamble. This documents a prerequisite; it does not change the gate's present error without dependencies.

## Design implications

The checks must have expectations written independently of product implementation. The package check should detect a separate application package for browser or server because the revised sentence expressly forbids it, without forbidding an unrelated future tooling package. The compiler-layout check should establish separate configurations and different output directories; the existing output check establishes that `npm run build` compiles both. The static-file check crosses the `src/server/**` trust boundary with direct and crafted paths and a foreign process working directory. The occupied-address check includes a normal-start control to prevent an always-failing process from satisfying the negative case. The code reviewer, not the check writer, creates each deliberate break from its sentence. None of these tests should rely on the ordinary tests as its oracle.

The change affects `foundations/invariants.md`, `foundations/decisions.md`, `foundations/part_map.md`, and four new invariant check files. D-06/2 *Verification* names both layout identifiers to keep its level-1 relationship complete. The part map must assign each new test file. D-04/2, D-05/2 and D-06/2 change only non-binding fields relative to /1. The product-foundation description changes exactly as accepted. The application code should remain behaviorally unchanged; a failing check is a concrete defect to resolve within the cycle, not a reason to relax the invariant.

Validation consists of `npm ci`, focused new checks with four deliberate breaks, existing product tests, the full invariant gate and the format guards of changed foundation files. The public/occupied checks exercise the running server. The gate and guards must report failures and unchecked results by name. No deployment/container behavior or TypeScript upgrade is part of this task.

## Self-review

The spec contains no open implementation placeholder. The chosen split preserves D-06's two clauses without changing its binding text. The package sentence explicitly rules out a second application package for either side, matching the intended check while allowing an unrelated tooling package. The two other invariant sentences match the earlier proposal and do not import unapproved MVP content. The accepted D-04/2, D-05/2 and part-map strings are exact; D-06/2 records all three checks. The /1 versions remain untouched, and the /2 rationale fields explain these field-only changes rather than recasting the original technical choices. The prerequisite is named in the invariants file without inventing a template field or promising the gate will mark missing dependencies unchecked. The planned four checks and deliberate breaks cover every new sentence. The agreed split and explicit package exclusivity are the recorded interpretations of the original combined sentence. The independent spec review's finding is resolved by this revision.
