## The open design matter (the spec settles it)

The first run of the cycle stored the remembered judgings in the game state and so in the saved game sent to the server (`src/browser/sim/types.ts` `RememberedJudging` and `GameState`, the strict load in `src/browser/sim/saved-game.ts`, the erasing in `src/browser/sim/judging-record.ts` with hooks in `game.ts`, `programs.ts` and `loop.ts`, the act in `judging.ts`, the view in `src/browser/view/maps-screen.tsx` and `maps-entry.ts` with `state-store.ts`). The human's remark 1 moves the remembered judgings out of the saved game into a cache in the browser (for example `localStorage`), keeps the behaviour (the last judging of each character–program–map triple: twelve results and what the judging took from the chest; the badge and the note of the stock; erasing when the program's rules, groups or plan of the trip change, when a death takes the character's practice and ranks, and when the program is deleted), keys the cache so that one game never shows another's judgings (the account, and a game after a reset), and brings the saved game's shape back to one without judgings (the version of the saved game stays raised only for the loop record: it stands at 9 in the code, not yet deployed). The cost accepted: on another device and after the browser's data is cleared the badges vanish until the next judging.

The spec decides **how**, in a form planning can cut into slices, and settles at least:

1. **What validates a cached judging.** The simulation is pure (D-04: no page, no storage, no clock) and the erasing used to be done by hooks inside the game state. With the cache outside the state, a cached judging must be recognised as stale without any hook: for example by what the entry stores beside the results — a fingerprint of the program's rules, groups with their order and plan of the trip (a rename changes nothing), and the character's generation number (D-218: it grows exactly at a death with no use of the resurrection left, which is the death `progressLost` — check this in the code and the decisions before you rely on it) — compared at the reading with the game state at hand. The deleting of a program needs no hook if program numbers are never reused (D-165 — check). Decide the fingerprint (a deterministic function of the program's content in the simulation's own code, with no browser API; its collision risk named), where the validity function lives (the simulation or the view), and what is done with entries that name a character, program or map the game state lacks. Where you judge another way better (hooks, a version counter kept in the state), give it with its price; the behaviour above stays.
2. **The key and the shape of the cache.** What distinguishes one game from another in the browser: the account, and a game after a reset — find what the game state or the account the view knows can tell (a field of the game state? the account's identity as the screens know it?) and decide the key; whether one entry per triple, one entry per game, or both; the stored form (a result of a seed as one letter?, the equipment as the clipped take list), and what happens at a corrupt, foreign or oversized value (ignored, never a crash), at a full or disabled storage (the judging still shows for the open page), and at another version of the cache's own shape.
3. **Where the code lives.** The browser's storage is the page's, not the simulation's: say which module of the view reads and writes it, how the act of a judging (`judgeAndRemember` through `store.act`, D-409) hands its result to it, how the screen's „Kto idzie” reads the mark from it, and that no file of the simulation touches storage. What of slice 7's `judging-record.ts`, of the hooks in `game.ts`, `programs.ts`, `loop.ts` and of `RememberedJudging` in `types.ts` and `saved-game.ts` goes away, what stays (the mark: the count solved, the badge, the note of the stock) and what moves.
4. **Concurrency and several tabs / a second device:** what the cache does when two tabs of one game write it, and what the player sees on a device with no cache.
5. **Whether any entry of the foundation or any invariant forbids the game to keep state outside the server's saved game.** The human's remark says: where such an entry or invariant stands (for example D-07), do not break it but make the fallback — a shortened form of a judging in the saved game and the removing of the least recently used judgings before the save passes its limit — and say which entry stopped it. Search the whole foundation (decisions, invariants, environment facts, the guidelines) — in particular D-07, D-117, D-206, D-209, D-211 and the invariant `expired-session-unsaved-progress`, D-04 and the invariants on the isolation of the simulation, and any rule on the browser's lasting storage or on what stays in the browser on a shared computer — and **conclude, with each entry quoted, whether the cache outside the saved game is forbidden**. The orchestrator's own reading, which you check and may overturn: D-211 forbids the *unsaved game state* in the browser's lasting storage (a progress that would stay for the next person at a shared computer); a cache of recomputable judgings is no progress and no game state, D-07 says what the server holds and what the browser computes and does not forbid a browser cache, and no entry forbids it; D-211's *Rejected* names „a new decision about the browser's storage” as a price, which the new decision pays. If you find that an entry forbids it, the spec designs the **fallback** (the shortened form in the saved game with the removing of the least recently used judgings before the limit; what the limit is, where it is measured and how the removing is chosen), and the report names the entry that stopped the cache.
6. **The foundation entries the change will write or change** (named, never worded): the new decision about where the remembered judgings lie (and its relation to D-211, D-07, D-206), the change of the decision on what the game remembers (it says the saved game keeps them), the entries of the saved game's shape that mention them, the glossary where a word changes; and the invariants or tests the change will touch.
7. **Checks the correction needs** (focused, at the lowest level that catches an error): the validity function's cases, the cache's cases in the page's test document (jsdom: `tests/view/page-document.mjs`; how `localStorage` is stood in), the strict load of a saved game without judgings, the screens' cases that stand today for the mark and the note.

What is out of the spec (planning takes them as they are): remark 3 — in the row of a character in „Kto idzie” whose own manual map run is open, the sentence „Wróć do niego i je zakończ” (or a part of it) becomes a link to that run's screen (the walk found the screen reachable only by its address `#/postac/3/przejscie`; where a link already stood before the first run of the cycle and the walk did not find it, the correction says so and changes nothing); remark 4 — the title of the trust-boundary case in `tests/sim/previous-programs.test.mjs` and the guideline line `guidelines/testing.md:177` that names it must not name the highest version number.
