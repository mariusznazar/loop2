# TypeScript 7 migration — design specification

## Intent and scope

Try to replace the application's exact TypeScript 6.0.3 development dependency with the latest stable 7.x release. Success means a clean Windows installation from the shared lockfile, the existing browser and server type checks and builds, and the product and invariant tests all work with TypeScript 7. If that outcome cannot be established within this task, leave the application on 6.0.3 and explain the blocker in the pull request. Linux building and execution belong to the first deployment task; they are unchecked here by the task owner's explicit answer. Node.js 24, the shared npm package, the two compilation configurations, and their separate output directories remain as the current product requires.

This is a bounded change under Superpowers brainstorming's classification: the existing dependency, build flow, and tests are present. The pinned the-way cycle nevertheless requires the architectural path's written spec and plan. This specification covers the design stage only.

## Current behavior and evidence

- `package.json` and `package-lock.json` pin TypeScript 6.0.3. `scripts/build.mjs` runs `node_modules/typescript/bin/tsc` with `process.execPath`, sequentially for `tsconfig.browser.json` and `tsconfig.server.json`; `--check` adds `--noEmit`. Successful builds also copy the browser HTML.
- Both configurations explicitly set `target`, `module`, `moduleResolution`, `lib`, `types`, `strict`, `rootDir`, and `outDir`. The browser excludes Node globals; the server excludes DOM globals. These settings preserve the configured target, module mode, strictness, source root and global type selection; neither configuration uses an option that the [official 7.0 announcement](https://devblogs.microsoft.com/typescript/announcing-typescript-7-0/) lists as removed. Other compiler and default changes still require verification through the real build and tests.
- The npm registry's [latest metadata](https://registry.npmjs.org/typescript/latest) reported 7.0.2 on 2026-10-07. The [published 7.0.2 tarball](https://registry.npmjs.org/typescript/-/typescript-7.0.2.tgz) contains `bin/tsc`, a Node ESM launcher. It imports `lib/tsc.js`, which resolves and executes the optional native package for the current OS and architecture. Therefore the existing Node invocation is structurally valid; installation of the native package and its actual execution remain to be verified on Windows.
- `application-build-output/1` tests real emitted JavaScript and negative probes. Its crossed-configuration assertions require exact `Cannot find name '<name>'` substrings. Whether TypeScript 7 retains them is unverified. A different diagnostic wording is a test compatibility problem only if the negative probes still prove that each configuration rejects the wrong global.
- The latest foundation requires server type checking before deployment and both compilation configurations to build, with one package and lockfile (`D-01/1`, `D-06/2`, `account-server-typecheck/1`, `application-build-output/1`, `application-build-layout/1`, `application-package-layout/1`). The build-tools part claims the manifest, lockfile, launcher, configurations, and affected invariant test. Its lockfile is a trust boundary.

## Approaches

1. **Direct exact-version upgrade, preserving the launcher (selected).** Pin 7.0.2 in `package.json`, regenerate `package-lock.json` through npm, and keep `scripts/build.mjs` unless an observed failure requires a small correction. This changes the fewest moving parts and preserves the existing command contract. Its cost is a new platform-native optional dependency, which Windows verification can cover but Linux remains for deployment work.
2. **Replace the launcher with `npm exec tsc` or a `.bin` command.** This uses npm's executable routing instead of the package path. It adds npm/shell behavior to the build path, and the published 7.0.2 package already supplies a compatible `bin/tsc` Node entry. Use this only if a concrete launcher problem is observed and the alternate route demonstrably fixes it.
3. **Keep TypeScript 6 alongside 7 through an alias or adapter.** This could retain the old compiler for tooling that imports TypeScript's API. This repository uses the CLI directly and has no such consumer. The extra compiler, lockfile complexity, and risk of calling the wrong `tsc` have no current benefit.

## Selected design

Update only the exact TypeScript dependency and lockfile first. Preserve Node 24 and the existing `build` and `typecheck` scripts, sequential compiler calls, configurations, and output paths. Use `npm ci` on Windows to establish that the lockfile installs the expected `@typescript/typescript-win32-*` native package and that the CLI reports 7.0.2. Inspect the resulting lockfile for registry URLs, integrity fields, platform package metadata, and unrelated changes; do not hand-edit integrity values or suppress optional dependencies.

Run the type check and build, then the product and invariant tests. Confirm that `--check` emits no files, both configurations emit valid JavaScript on build, and the type-error probes still make the commands fail. A successful launcher alone does not prove compiler behavior.

If the crossed-configuration probes fail only because TypeScript 7 changes diagnostic wording, return to the foundation step before modifying `tests/invariants/test_application_build_output.py`. Keep the invariant sentence and its behavioral coverage: each wrong global must cause a nonzero build, with output tied to the inserted source file and the missing name or a stable equivalent compiler diagnostic. The test's author must be independent of the implementation author, and its reviewer must deliberately break the check as WAY-69 requires. Do not weaken it to merely assert a nonzero exit or remove a negative probe. Any observed actual type-check or emit difference is a product compatibility issue to diagnose and fix within the task's narrow build/compiler scope, not a reason to redefine the invariant.

No TypeScript version or native-launcher foundation decision is proposed. The current decisions specify TypeScript, Node 24, two configurations, and one package, rather than a particular compiler release or launcher implementation. The migration does not itself create a lasting product rule about which TypeScript minor version must be used. The foundation return step must revisit this judgment against the final diff and any newly learned fact that a decision or invariant needs.

## Verification and fallback

After the dependency change, run on Windows: clean `npm ci`; `node node_modules/typescript/bin/tsc --version`; `npm run typecheck`; `npm run build`; `npm test`; and the invariant gate through `python -B .the-way/gate/run_tests.py tests/invariants --record .runs/invariant-tests.jsonl`. Run the applicable part tests and changed foundation format guards before merge, with the correct task base and merge target. Record each failure and each unrun check, especially Linux, separately. Inspect the generated server and browser outputs and the native package selected by npm. The existing invariant probes supply adversarial input checks for build and type isolation; review the lockfile's new external package entries as trust-boundary data.

If 7.0.2 fails, attempt only fixes justified by an observed compatibility issue in the compiler invocation, configuration, or diagnostic assertion while retaining the foundation's behavior. The fallback criterion is failure to obtain clean Windows installation, typecheck, build, product tests, and invariant gate after those scoped corrections, or a required correction that would violate the existing product decisions/invariants. Then revert the attempted product changes to the exact 6.0.3 manifest/lockfile state, verify the fallback state on Windows, and deliver the failure evidence in the PR. Do not claim Linux verification from Windows results.

## Stage boundary

This is the self-reviewed design artifact. Its implementation details are provisional under the task owner's delegation to the cycle orchestrator; human review occurs at the pull request. Planning and implementation are outside this design handoff.
