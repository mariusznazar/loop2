# Szyfrowana droga od Cloudflare do serwera gry

Status: ready for cycle
Project relation: plan item: plan_mvp_loop2.md — 22 szyfrowana-droga-do-serwera

## Description

### Need

- Dziś Cloudflare łączy się z serwerem testowym zwykłym HTTP, a port gry jest dostępny z internetu przez IPv6 hosta z pominięciem Cloudflare (plan, § Open questions, notatka pod pytaniem o sekret `express-session`: „Port aplikacji jest dostępny bezpośrednio przez IPv6.”).
- Decyzja D-10 pozwala na zwykłe HTTP od Cloudflare do serwera tylko “while no player account is served through this route”, więc zanim zadanie 15 zacznie obsługiwać konta graczy na serwerze testowym, ta droga musi być szyfrowana, a port gry zamknięty dla internetu (plan, dziennik zmian 2026-10-25, linia o dodaniu zadania 22).
- To zadanie zmienia drogę ruchu na serwerze, który jeszcze nie trzyma kont, tak że jej wynik — szyfrowany tunel i zamknięty port — sprawdza się osobno, przed kontami (pytanie 1).

### To do

1. Gra pod `https://loop2.mariusznazar.com/` odpowiada przez Cloudflare Tunnel: program `cloudflared` działa jako druga usługa projektu Compose loop2, w osobnym kontenerze obok kontenera gry, z własnym limitem pamięci, a jego wersja stoi w repozytorium i wdraża się tą samą drogą co gra (pytanie 2).
2. Kontener gry nie publikuje portu na adresie hosta osiągalnym z internetu, więc port aplikacji przestaje być dostępny z pominięciem Cloudflare (pytanie 1).
3. Wdrożenie uruchamia obie usługi, a jego sonda sprawdza grę bez portu publikowanego na zewnątrz; wdrożenie, które nie uruchomi gry albo `cloudflared`, kończy się błędem z linią przywrócenia, jak dziś (pytanie 2: „D-10 i sonda wdrożenia do przepisania”).
4. Token tunelu leży na serwerze w pliku poza checkoutem, a Compose podaje go z tego pliku kontenerowi `cloudflared`; wymiana tokenu kończy się nowym startem kontenera `cloudflared` (pytanie 4).
5. Fundament dostaje nowe brzmienie D-10, D-13 (plik z tokenem na serwerze jako miejsce sekretu), uzasadnienia D-15 (dwa kontenery i dwa obrazy loop2), D-17 i niezmiennika `loop2-host-sharing`, a testy niezmienników wdrożenia, które dziś zakładają jedną usługę Compose, sprawdzają te niezmienniki dalej przy dwóch usługach (pytania 2 i 4).
6. Skill wdrożenia `loop2-deploy`, w obu kopiach (`.claude/skills/loop2-deploy/` i `.agents/skills/loop2-deploy/`), opisuje nową drogę ruchu (pytanie 5):
   - czynności człowieka przy pierwszym uruchomieniu tunelu, w kolejności z pytania 3, w tym instalację skryptu z commitu requestu przed jego ręcznym wdrożeniem (dzisiejsza procedura, `references/troubleshooting.md:44`–`48`, kopiuje skrypt z checkoutu, który przed tym wdrożeniem stoi na ostatnio wdrożonym commicie `main`);

   - odczyt limitu pamięci kontenera `cloudflared` zawężony do samego pola limitu, tak by odczyt agenta nie wypisał tokenu;

### Acceptance criteria

- Żądanie do portu gry wysłane spoza hosta, na adres IPv6 hosta, nie dostaje odpowiedzi gry, a `https://loop2.mariusznazar.com/` w tym samym czasie odpowiada stroną gry — obserwacja człowieka przy requeście.
- Nieznana ścieżka `/api/` pod `https://loop2.mariusznazar.com/` dostaje przez tunel błąd API w JSON, nie stronę gry (D-05; niezmiennik `loop2-api-error-route`) — obserwacja człowieka przy requeście.
- Kontener `cloudflared` działa z zastosowanym limitem pamięci — żądany limit odczytany samym polem limitu (np. `docker inspect --type container --format '{{.HostConfig.Memory}}'`), nie pełnym `docker inspect`, i limit egzekwowany jak dla kontenera gry — obserwacja człowieka przy requeście (D-17: “a Compose service with no memory limit” jest naruszeniem).
- `https://kantarion.bieda.it/` działa jak przed zmianą, a kontenery `loop` i `foundryvtt` stoją nietknięte.

## Decisions in play

- D-05 „What serves the built game and account requests in the container?”: “One Node.js process running Express 5 serves both the built game's static files and the `/api/` account and save routes in the loop2 container. An unmatched `/api/` request receives an API error, not the game's HTML page.” — przez tunel dalej obowiązuje.
- D-08 „Where does the game run?”: “The game and its account and save server run in a dedicated loop2 container on Mikrus, at a public address different from `kantarion.bieda.it`. The existing loop container remains untouched.” — `cloudflared` stoi w osobnym kontenerze; kontener gry zostaje.
- D-10 „How do players reach loop2 on the server?”: “Players reach loop2 at `https://loop2.mariusznazar.com/`, which Cloudflare proxies to the server: a proxied AAAA record points at the server's IPv6 address, and an Origin Rule sends the requests to the port the loop2 container publishes. Players connect to Cloudflare over HTTPS, and Cloudflare connects to the server over plain HTTP only while no player account is served through this route.” — przepisuje ją to zadanie (pytanie 2; wiersz 1 *Settlements to record*); jej weryfikacja: “violates: a public address on a Mikrus subdomain for loop2; a task that serves player accounts through this route while Cloudflare still connects to the server over plain HTTP”.
- D-11 „Which branch deploys loop2 to the test server?”: “The deploy branch is `main`: a push to `main`, the merge of a pull request included, reaches the test server without anyone starting it by hand, deployed itself or within a later commit of `main` that contains it.” — każde scalenie innego zadania wdraża się samo, także w trakcie przełączania drogi (pytanie 3).
- D-12 „What access to the server does an agent have?”: “An agent reads the server only through the `mikrus` MCP server and changes nothing on it. Every change on the server that is not a deployment started by the automation is made by a human.” — sprawdzenie portu 7844 to odczyt (pytanie 7).
- D-13 „Where do the server's access values and secrets live?”: “Secrets and the values that give access to the server — its name, SSH port, SSH user and IPv6 address — stay outside the repository, in the repository's GitHub secrets and the owner's private note, and the repository's files and requests refer to them by the secret's name or the note. The server directory, the container port and the deploy script may stand in the repository.” — dostaje plik z tokenem tunelu na serwerze (pytanie 4; wiersz 3 *Settlements to record*).
- D-15 „How is loop2 recovered when a deployment goes wrong?”: “A deployment that stops before it starts the new container leaves the running loop2 container in service. A rollback is a deployment of an earlier commit — a revert merged to `main`, or a human's run of the installed deploy script with that commit, which may name a commit of any branch of the GitHub repository while the automation's key deploys only commits of `main`. No earlier image is kept, so a rollback restores the earlier commit's code, never the data of that time.” — uzasadnienie: “keeping no earlier image leaves the server one checkout and one image of loop2” (pytanie 2).
- D-16 „What does the automation's key run on the server?”: “The automation's key runs only a root-owned installed copy of the deploy script […]. Each deployment compares that copy with the script's source at the deployed commit and only warns when they differ, and reinstalling the copy is a human's change.” — tokenu nie podaje się kluczem automatu (pytanie 4).
- D-17 „How does loop2 share the Mikrus host with other workloads?”: “A deployment of loop2 changes nothing on the host but loop2's own checkout, image, container, log and lock, and the build cache and base image its build adds to the Docker store the host's workloads share, which it never prunes; it removes or replaces nothing of another workload. It builds only while the host's available memory and free disk stay above thresholds the repository sets, and the loop2 container runs under a memory limit.” — przepisuje ją to zadanie (pytanie 2).
- D-28 „Which coding-guideline discipline does loop2 adopt?”: “[…] while deferring automatic formatting of Python and Bash and separate exemplars for building, deployment, entry points, HTML and CSS; session, saved-game and mail exemplars are selected with their first implementations, and any deferred existing kind is compared before its exemplar is selected. […]” — zadanie nie wybiera wzorca wdrożenia, więc nie porównuje plików (Context, wytyczne).
- Niezmiennik `loop2-host-sharing`: “A deployment of loop2 stops, removes, replaces or reconfigures no container, image, network or volume on the host other than loop2's own, and the loop2 Compose service asks the host for no privilege that a default container lacks.” — przepisuje go to zadanie (pytanie 2).
- Niezmiennik `loop2-container-isolation`: “The loop2 instance runs in a container separate from the existing loop instance.”
- Niezmiennik `loop2-one-serving-process`: “One Express 5 process in the loop2 container serves both the built game and `/api/` account and save requests.”
- Niezmiennik `loop2-api-error-route`: “An unmatched `/api/` request receives an API error response, never the built game's HTML page.”
- Niezmiennik `loop2-deploy-keeps-running`: “A deployment that stops before it starts the new container — at its input, the commit, the lock, the reading of memory and disk, the fetch, the checkout, the type check or the build — leaves the running loop2 container in service.”
- Wpisy rzutowane definicji: plan nie przypisuje temu zadaniu żadnego (plan stojący na definicji o odcisku 7692b28a: tabela wpisów rzutowanych i dziennik zmian 2026-10-25, linia o dodaniu zadania 22); zadanie zachowuje prawdziwość „(new) — What public address do the game and account server share?”: “The built game and the account and save server use one public HTTPS origin at loop2's address.” (definicja zatwierdzona 2026-10-26, odcisk 7692b28a; wpis urzeczywistniają zadania 2 i 15, zapisuje zadanie 15).
