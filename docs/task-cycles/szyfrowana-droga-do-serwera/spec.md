# Spec — Szyfrowana droga od Cloudflare do serwera gry

- Task: `.runs/task-cycles/szyfrowana-droga-do-serwera/task-frozen.md`
- Open choice: token delivery and permissions, immutable tunnel image and its ownership, internal probing, readiness, transport, memory limit and rotation.

## Intent

Players continue to open `https://loop2.mariusznazar.com/`, but traffic from Cloudflare reaches the host through an encrypted Cloudflare Tunnel. The application stops publishing a host port. This establishes the route before the separate task adds accounts and sessions.

## Goals and non-goals

The Compose project owns two separately limited containers, `app`/`loop2` and `cloudflared`/`loop2-cloudflared`. A deployment prepares both images before replacing either container and succeeds only after both are healthy and the application's internal HTTP probe succeeds. The two deployment skill copies describe setup, observation, token rotation and rollback through this route change. All three accepted settlements become foundation entries.

Accounts, sessions, Express proxy trust, changes to the old game's route, host firewall changes, zero-downtime deployment, new automation credentials, remote tunnel configuration in the repository and automatic token management are outside this task. The five external actions remain the human's at the blocked draft request.

## Constraints

- D-05 and `loop2-one-serving-process` concern the application container: it retains one Express process serving the game and API. The tunnel connector is a separate process in a separate container.
- D-09, D-11 and D-16 keep the two existing deploy input paths and the root-owned installed script; no deployment changes its installed copy or transports secrets through the automation key.
- D-12 and D-13 keep server and Cloudflare mutations with the human and keep access values and secrets out of repository files, requests and shared logs.
- D-15 and `loop2-deploy-keeps-running` preserve the running application before the switch. The new preparation path preserves the running tunnel too. No host-wide cleanup, no changes to `loop` or `foundryvtt`, and no retained product image for rollback.
- The resource gate remains 1024 MiB available memory and 4 GiB Docker-filesystem free space, read before image preparation. The orchestrator's 2026-10-26 observation was 4352 MiB total, 3707 MiB available, zero swap. That observation does not establish future headroom or tunnel memory demand.
- The frozen task's TCP/IPv4 observation concerns the host to one Cloudflare endpoint on port 7844; container connectivity, UDP and other endpoints remain unproved until deployment.
- The approved H1–H5 sequence forbids other merges from installation of the request's script until this request is merged. The interval after H4 and before H5 is an accepted outage.
- The existing deployment code kind has no selected exemplar (D-28). The small additional Dockerfile is another file of that existing kind; this task selects no exemplar or additional guideline discipline.

## Decisions

### 1. The route and its two containers

Remove application host-port publication altogether, including loopback publication. Retain the Compose project's ordinary private bridge network; use neither host networking nor an external network. The human configures the remotely managed tunnel's published application to forward the existing public hostname to `http://app:3000`. The HTTP hop stays inside the host's Compose network; encryption covers the connection between Cloudflare and `cloudflared`.

The application keeps its 512 MiB limit. Choose 256 MiB for `cloudflared`, a bound to be tuned from deployment observations, not a measured requirement. Both retain restart behaviour after host restart. Keep tunnel metrics bound to its own loopback, `127.0.0.1:2000`, with no published metrics port.

A loopback-published application port would allow the old host curl probe but would retain unnecessary publication and another host socket to manage. A third probing container would add an image and a runtime unit solely to repeat capabilities already present in Node. No published port plus an internal probe is the smaller arrangement. A 128 MiB tunnel limit would spare another 128 MiB of possible usage but risks an unmeasured low ceiling; 256 MiB allows more headroom while limiting total application-plus-tunnel usage to 768 MiB. A larger limit would grant more shared-host memory without evidence of need. A wrong limit can cause connector restarts; H4/H5 must observe the applied and enforced limit and revise before acceptance if it fails.

Docker documents that unpublished bridge-network ports are blocked externally by default and remain available to the host and same-network containers; the external IPv6 acceptance observation is still required because source inspection cannot prove the host's actual routing. Source: https://docs.docker.com/engine/network/port-publishing/ (read 2026-10-26).

### 2. Official image, with product ownership

Build a minimal loop2-owned connector image using `deploy/cloudflared.Dockerfile`. Its base is the official `cloudflare/cloudflared:2026.10.4` image, pinned additionally to `sha256:c6c7ae1d5dfdcb094ad344ed68ccffc26635c9c6be80965664c33baf064b0515`. The file adds the existing loop2 image ownership label, `org.opencontainers.image.title=loop2`, and otherwise inherits the upstream executable, nonroot identity and entrypoint; it installs no shell or other software and copies no token. Compose builds this image as the `cloudflared` service. An update changes the version and digest together in the repository and follows ordinary deployment.

The existing successful-deployment cleanup of dangling images carrying that label covers the replaced product images for both services. Upstream base images and shared cache remain untouched, just as the Node base remains untouched. Rollback rebuilds an earlier commit, rather than selecting a retained earlier product image. Neither the task nor this choice promises that Docker's shared layer store contains exactly two images.

Using the upstream image directly is shorter but leaves no product ownership label for the existing restricted cleanup; removing shared registry images or introducing a separate tag-and-image-ID cleanup protocol would add risk and code. A floating tag permits an upstream replacement without a repository change. The selected wrapper adds one short Dockerfile and a cached metadata build, keeping cleanup unchanged. An unavailable pinned base fails during preparation, while the old containers still serve.

Evidence supplied by the orchestrator: `docker pull cloudflare/cloudflared:2026.10.4` exited 0; the image inspection returned the digest above and `Config.User` of `65532:65532`. The tagged upstream Dockerfile confirms this user and the cloudflared entrypoint with auto-update disabled: https://raw.githubusercontent.com/cloudflare/cloudflared/2026.10.4/Dockerfile (read 2026-10-26). The release is https://github.com/cloudflare/cloudflared/releases/tag/2026.10.4.

### 3. Token file and rotation

Choose a Compose file-backed secret named `cloudflare_tunnel_token`, sourced from `/etc/loop2/cloudflared-token` and granted only to `cloudflared` at `/run/secrets/cloudflare_tunnel_token`. The connector reads that path through `--token-file`. No token value goes into Compose environment, command arguments, build context, GitHub secrets or output. The existing five GitHub secrets retain their purpose.

The human creates `/etc/loop2` owned by the deployment run account, group ID 65532, mode 0750, and the token file with the same owner and group, mode 0640. Thus the run account can manage/read it, processes with group 65532 (including the connector) can read it, and root retains access; users outside that owner/group receive no access through the ordinary mode bits. This works for either a root or nonroot deployment account. Do not override the container user to root and do not make the file world-readable. The private note holds the second copy. File-backed Compose secrets are read-only mounts; their `uid`, `gid` and `mode` attributes do not remap host-file ownership, so rely on the host permissions rather than decorative Compose permission fields.

A normal deployment force-recreates both service containers, including redeploying the same commit. Token rotation is a human sequence: refresh the token in Cloudflare, replace the server file with the same owner/group/mode, update the private note, then run the installed deploy script for the currently running application commit and verify success. This deliberately rebuilds/rechecks the commit and incurs the usual short outage; it avoids a separate restart command using a checkout that may be left at a failed commit. Recreation also remounts an atomically replaced token file. A plain Compose restart is not the documented rotation operation.

`env_file` would simplify file ownership to the deploy account alone but would place the token in container environment and expose it to full inspection/configuration output. An ordinary arbitrary bind mount would work but would introduce a broader mount interface than one explicitly granted secret. The selected secret adds narrow top-level and service `secrets` validation and requires numeric host-group permissions. If those permissions are wrong, the connector cannot start; its readiness failure fails deployment before any public-route acceptance.

Sources: token-file support and protocol parameters, https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/configure-tunnels/run-parameters/; file-secret ownership caveat, https://docs.docker.com/reference/compose-file/services/#secrets; secret grants, https://docs.docker.com/reference/compose-file/secrets/; refreshed tokens do not terminate existing connectors, https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/configure-tunnels/remote-tunnel-permissions/ (all read 2026-10-26).

### 4. Transport and readiness

Use `http2` with edge IP version `4`, explicitly. This matches the available host TCP/IPv4 evidence and avoids waiting for an unproved UDP route before fallback. It still requires successful connection from the actual container. `auto` would try QUIC before HTTP/2 and could work but adds an unproved transport and fallback delay. Forcing QUIC would rest on no evidence. HTTP/2 gives up QUIC's transport characteristics and post-quantum key agreement support; neither is a task requirement. Wrong IPv4/container assumptions produce a readiness failure and require diagnosis, not a silent fallback to a public application port.

The connector health check invokes its existing `cloudflared tunnel --metrics 127.0.0.1:2000 ready` command in exec form. No shell/curl is assumed inside the distroless image. Docker bounds each health-check execution; use the application's current 5-second interval, 3-second timeout, 5-second start period and 3 retries. The deployment retains a 120-second health wait for both services. Readiness means at least one active connection to Cloudflare; it does not establish that the public hostname or application forwarding is configured correctly.

The upstream command calls `/ready` and exits unsuccessfully for a non-200 response; the endpoint yields 200 only with active edge connections. The orchestrator's local CLI check returned exit 1 for connection refused when no connector was running, confirming the real command exists. Sources: https://raw.githubusercontent.com/cloudflare/cloudflared/2026.10.4/cmd/cloudflared/tunnel/subcommands.go (buildReadyCommand/readyCommand); https://raw.githubusercontent.com/cloudflare/cloudflared/2026.10.4/metrics/readiness.go. TCP port 7844 and endpoint roles: https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/configure-tunnels/tunnel-with-firewall/ (read 2026-10-26).

### 5. Deployment units and failure contract

The existing installed Bash script remains the orchestrating unit. It takes the same validated commit input and depends on Git, Docker/Compose and the host resource readings. Extend its preparation unit to build both `app` and `cloudflared` before the first Compose start/recreate. An app build failure, connector base pull failure or connector build failure returns the existing exit 7 and leaves both old containers untouched. Preparation does not read or print token content. Missing/unusable secret detected by Compose at start returns exit 8; no automatic repair or token fallback is attempted.

The switch unit explicitly starts both services in the loop2 project, without building at switch time, force-recreates them and waits for both health checks. A failure of either service returns exit 8, records the previous application commit and restore line, and preserves the current policy of putting Docker output and the last bounded logs of both services in the server deploy log rather than Actions output. The switch is not atomic: after it begins, partial availability is possible and the restore instruction is required.

The application probe unit runs the container's existing Node executable through Docker exec, requests only its own `127.0.0.1:3000/` and fixed unknown `/api/` path, and returns status and content type to the script. Preserve the required outcomes: root 200 and unknown API 404 with JSON content type. Bound each HTTP request to 10 seconds and the Docker exec invocation to 15 seconds. No persistent second server, host port, new container or extra application dependency is added. Nonzero execution, timeout or wrong status/type returns exit 8 with the restore line. The probe is read-only with respect to product data; its transient Node client is not a second serving process.

Keep the public workflow probe and old-game check. H5's public page/API and outside-host IPv6 observations remain the actual proof of route wiring and external closure. The restore line must direct the operator to the additional script/Cloudflare steps when crossing this route change, so it does not imply that running the earlier SHA alone restores public traffic. The deployed revision remains the application container label, not the checkout or connector image.

Using only `running` state for the connector would allow a disconnected tunnel to report deployment success. A public URL as the H4 readiness gate would prevent the approved sequence, since H5 publishes the hostname after H4. Internal application HTTP plus connector readiness permits that sequence and honestly leaves public-route acceptance to H5. Sources for Compose wait/recreation semantics: https://docs.docker.com/reference/cli/docker/compose/up/ (read 2026-10-26).

### 6. Checks remain specific to what they prove

Adjust the existing one-service assumptions to the two named services, rather than weakening them to accept arbitrary services. The one-serving-process check applies to `app` and the application's Dockerfile. Isolation requires distinct loop2-owned container names, no external network or Docker socket and no general volume sharing. Host-sharing continues to read the entire Compose document and deny unknown keys and commands. Its new allowance is exactly the one named file-backed secret at the selected host path, granted only to the connector; it does not permit arbitrary secrets, environments, mounts or external sources. The new Docker exec allowance is restricted to the application container and the internal Node probe, with no privileged/user escalation or arbitrary target.

Two further existing checks require the same role distinction: `test_account_server_runtime.py` currently requires a Node base in every Dockerfile, and `test_account_server_typecheck.py` currently requires every Compose service to build from the application Dockerfile. Keep their full application Node-24 and predeployment type-check protection while explicitly recognizing the named connector image as the approved non-application service. Do not replace this with a general exemption for arbitrary non-Node Dockerfiles or arbitrary services. These changes touch build-tools tests; that part's map entry and the already applicable coding/testing guidelines bind them. D-01 describes the account server, not the external connector.

Give the new internet-port-closure invariant a standing source test that rejects published application ports and host/external network bypasses, and show it fail on a crafted exposure. Retain the external human acceptance check because source configuration cannot prove the host. Preserve the crafted-input and wrong-branch refusal tests of the deploy boundary, and preparation-failure coverage. Add direct coverage that either image's preparation failure cannot reach the switch, that either service's failed readiness causes exit 8 with restore information, and that incorrect internal HTTP outcomes cannot report success. Controlled Docker answers demonstrate script decisions; they must not be described as proof of real Docker, tunnel authentication or Cloudflare availability.

Use real local HTTP/process/container checks for the changed probe and image capabilities, where the local environment permits them, without a real tunnel token. Real token-file readability and authenticated readiness are checked by the human deployment. All permanent tests run through `npm test`, and a newly added Python test must be observed in that gate. No standalone selection or weakened expectation is introduced to save time. No browser visual/event or whole-journey automation condition is triggered by this transport-only change.

### 7. Operating instructions and rollback

Both copies of `loop2-deploy` and both sets of references receive the same complete instructions. Keep initial host/keys setup useful, but remove assertions that main has no script and distinguish initial provisioning from this route's five human actions. H1 creates the remote tunnel without a published name; H2 provisions the file and private copy; H3 fetches the request's exact commit and installs its extracted, syntax-checked script root-owned 0755 while preserving the pre-transition `.previous`; H4 deploys that commit; H5 removes loop2's AAAA, Origin Rule and Configuration Rule and publishes the tunnel hostname to `http://app:3000`. No old-game setting changes. Corrections during the window reinstall from the new request head if needed without destroying the pre-transition recovery copy.

The instructions must show the full rollback through the transition for both fast rollback and a revert: install the script from the target commit before deploying that commit, remove the tunnel's published application and its loop2 CNAME, then restore loop2's proxied AAAA and its two hostname-scoped rules. For a revert, install the script extracted from the revert request's target content before merging the revert so automation uses the matching script. Show the action count and the temporary outage; describe data as unaffected by this task, not generically restorable from Git. For abandonment after H3, restore the preserved pre-transition script, redeploy the pre-transition main commit if H4 occurred, and restore DNS/rules if H5 occurred. Optional removal of the unused tunnel/token is a later human cleanup, not an agent action. Record the accepted no-other-merges window through completion.

Agent reads remain narrowly scoped. Memory inspection prints only `HostConfig.Memory` for each named container (512 MiB = 536870912; 256 MiB = 268435456); enforced limits come from the limit column of scoped `docker stats --no-stream`. State, revision, health and bounded service logs stay allowed; token content, full inspect and Compose configuration dumps are not diagnostic reads. Add read-only internal application probing with the selected Node probe and connector readiness/status inspection to match the new route. Agents do not restart containers or rotate secrets.

The permanent outbound diagnostic is the task's bounded host check: `timeout 8 curl -4 -v --connect-timeout 5 -o /dev/null telnet://region1.v2.argotunnel.com:7844`. The documented success evidence is curl's connected line, often followed by timeout exit 124, not exit 0; a connection failure is different. The output is not proof of container connectivity or UDP. The same bounded check for region2 may be documented as the other official endpoint, but the recorded environmental observation covers region1 only. Diagnose token/read-permission errors, disconnected connector, and public routing separately; 1016 is a possible stopped-tunnel symptom, not a unique diagnosis. Do not propose opening port 18080 to repair the tunnel.

Cloudflare's docs establish the CNAME target and possible stopped-tunnel 1016 response at https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/routing-to-tunnel/dns/; CNAME and same-name AAAA cannot coexist, https://developers.cloudflare.com/dns/manage-dns-records/troubleshooting/records-with-same-name/ (read 2026-10-26).
